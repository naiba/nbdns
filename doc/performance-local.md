# 本机端到端性能验证与优化记录

## 环境和边界

Go 1.27.2 linux/arm64；目标进程 GOMAXPROCS=2，生成器 GOMAXPROCS=2，共享 3 CPU 的 cgroup 配额。真实 NbDNS 进程、真实 UDP/TCP/HTTP DoH 请求、本机模拟上游，加载 50,000 条过滤规则，开启统计及仅本机 profiling。没有操作路由器。

基线为 v2.0.1（bf6429c），不是 v2.0.0。主矩阵候选包含 handler 优化，不包含随后发现的 TCP 断线重试修复。因此不能将主矩阵直接视作最终代码验收。

每个版本 10 场景 × 3 并发（1/16/64）× 3 重复，每组 3 秒；180 组累计 20,628,978 次请求，响应校验错误为零。校验内容包括 ID、question、响应标志、RCODE、地址。失败测试不进入性能比较。

## 扩展测试发现（历史阶段，后续修复见下）

1. TCP 上游每连接达到查询次数上限后关闭，原代码直接将下一次查询判失败。新增红绿回归测试，验证一次只读 QUERY 重试；多个闲置连接均关闭时，重试必须建立新连接，不能再次取到另一个过期连接。不重试超时、协议错误或 UPDATE。
2. 64 并发 TCP 冷启动仍可触发连接池 `DialMaxConcurrency:20`，即使测试配置允许 128 活跃连接，也会出现 `reached OpenMaxConcurrency`。这是独立的容量/突发行为，**当时未修复；后续已调整为配置容量并通过 c64 测试**。默认 50 活跃连接也是另一项限制。
3. 本机临时端口的 TCP/UDP 冲突曾导致服务监听失败；测试程序改用临时源端口范围之外的监听端口，并同时探测 TCP/UDP。此前失败扩展结果弃用。
4. 16 并发扩展测试与持续负载观察另行运行；最终发布前仍需确认结果、复测最终二进制及处理上述突发限制。

## 数据与复现

工具说明见 `cmd/dnsperf/README.md`。原始数据位于本机 `/root/nbdns-performance/end-to-end/`：`validated-baseline.jsonl` 与 `optimized.jsonl` 是主矩阵，`comparison.json` 是汇总；`profile-baseline/` 是独立 profile。早期 `baseline.jsonl` 具有错误 TCP 测量，禁止使用。

这是 closed-loop 测量，不能代表固定开放到达率下的尾延迟。HTTP DoH 不包含 TLS、SOCKS 或互联网延迟。内存分配计数包含少量诊断开销，HeapBytes 不是 GC 后保留内存；RSS 每 20ms 采样。后续已补齐本机 TLS/DoT、混合、超时及五分钟持续负载；公网代理与多日稳定性不在本次本地实验范围。未发布新版本。

## 后续五分钟对照与内存定位

以下均为 c16、300 秒、本机合成负载，每版每场景一次；不是三次重复的中位数。

|版本|唯一域名写入 QPS / P99 µs|混合流量 QPS / P99 µs|唯一写入强制 GC 存活堆 MiB|
|---|---:|---:|---:|
|v2.0.1 基线|12,580 / 3,410|38,570 / 1,665|83.4|
|handler + TCP 修复|13,983 / 3,105|42,000 / 1,509|118.8|
|增加小尺寸压缩表与两个 memtable|13,543 / 3,344|41,513 / 1,541|44.1|

六组共 48,676,612 个请求，校验错误为零。原始数据为 `long-{baseline,final,bounded}.jsonl`。混合流量固定比例为 60% 热缓存、20% 唯一写入、10% 自定义记录、10% 过滤。

`long-final` 的压缩构建器存活分配约 108 MiB，`long-bounded` 约 32 MiB；Badger 默认 TableSizeMultiplier=2，随层级增长构建器，原先仅限制 memtable 不够。保持基表尺寸并将 multiplier 设为 1，同时显式设置 NumMemtables=2（默认实际为 5，而非原注释声称的 2）。该调整经失败/通过回归验证。

RSS 不能用存活堆替代：唯一写入各分钟 RSS 中位数基线为 180/316/381/463/557 MiB，受限构建器候选为 158/264/362/465/564 MiB，仍随磁盘数据及映射增长。对无限新域名输入，不能声称 RSS 已稳定或受 8 MiB 热缓存限制。固定工作集补充结果见下。

TCP 冷启动增加了确定性屏障测试：64 个并行 bootstrap/dial 必须全部到达，不能被隐藏的 20 个建连名额拒绝；每个返回包均检查 ID/question/rcode。UPDATE 不因旧连接关闭而重试。TLS 测试用测试 CA 验证证书，不关闭证书验证。

`final-matrix`、`complete-matrix`、`observed-matrix` 在连续执行时存在少量 SERVFAIL，整套不作为有效性能结果；独立长测无错误。端口分配与 TIME_WAIT/网络资源相关性尚需诊断，不能将其直接归结为产品回归或完全宣称已修复。

### 固定工作集的五分钟补充

10 万域名轮转（大于 2,048 条热缓存，实际包含 Badger 读），基线/最终候选共 20,320,214 次请求、零错误，上游各 100,000 次。QPS 33,650 → 34,068，P99 1,693 → 1,646 µs；峰值 RSS 95.6 → 88.9 MiB，结束 RSS 63.1 → 60.8 MiB；结束 PSS 文件映射约 28 MiB。固定集合未出现无限新域名测试那样的持续 RSS 增长。这支持“写入工作集增长与数据库压缩/文件映射是主要因素”，但不等同于证明所有运行条件均无泄漏。

### 连续矩阵偶发 SERVFAIL 已定位到系统发送失败

通过 Go build overlay 构建仅记录错误、不开启全量 debug 的诊断二进制，复现 61 次错误。全部对应 `write udp 127.0.0.1:<source>->127.0.0.1:18156: write: operation not permitted`，发生在 UDP 系统发送阶段，上游实际收到的请求恰少 61 次。这不是 DNS 校验拒绝、超时、缓存损坏或 TCP 池容量错误。具体宿主机安全/网络策略未越权修改；不把 EPERM 自动重试加入产品以掩盖环境限制。诊断产物 `error-isolation/` 不能用于性能比较。10 秒间隔的最终矩阵与独立五分钟连续负载均零错误，因此本次本地实验完成；结果只适用于记录的环境与负载，不构成公网/多日可靠性保证。
